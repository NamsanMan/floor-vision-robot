# 로봇에서 추론 vs PC에서 추론

같은 INT8 모델과 같은 ONNX Runtime(1.23.2)으로, 추론하는 곳만 다르다. PC에서 추론할 때 로봇은 240×320 JPEG(약 11.5 KB)를 보내고 바닥과 바닥이 아닌 부분의 경계를 알기 위해, 두 채널(class)의 logit 차(float16, 60×80, 9.4 KB)를 받는다. 경계 찾기, 좌표 변환, blind-spot memory, 발행은 같은 코드다. PC는 유선 네트워크를 이용하고, 로봇은 2.4 GHz Wi-Fi에 연결되어 있다.

## 정지 상태에서 측정 (60초씩 번갈아 두 번, Nav2 없음)

| | 로봇 추론 | PC 추론 |
|---|---|---|
| 지연 중앙값 / p99 | 104\~105 / 141\~167 ms | 30\~32 / 42\~48 ms |
| 로봇 CPU / 인식 노드 | 45~46% / 0.9코어 | 22~23% / 0.11코어 |

지연은 카메라 영상 시각부터 장애물 point를 발행하기 직전까지다(전처리·추론·후처리 포함, PC 추론이면 통신도 포함, 로봇 시계 기준). PC 쪽 왕복 23 ms는 처리 13 ms와 전송 약 10 ms로 나뉘었다. 원본 영상(640×480)을 그대로 보내면 초당 5장에 37 Mbps라 로봇 Wi-Fi 실효 대역(약 40 Mbps)을 거의 다 쓴다. 줄여서 JPEG로 보내면 0.47 Mbps다.

## 주행 중 측정

| | 로봇 추론 (09·12회차) | PC 추론 (15회차) |
|---|---|---|
| 지연 중앙값 / p99 / 최대 | 137\~146 / 250\~280 / 300 ms 안팎 | 38 / 54 / 60 ms |
| 로봇 CPU / 인식 노드 | 73~76% / 1.0코어 | 45% / 0.13코어 |

## 연결 끊김 test

정지 상태에서 PC에서 돌던 추론 서버 `offload_pc.py`를 끄자 0.62초 뒤 감시 노드가 정지 신호를 냈다. 주행 중(16회차)에는 3.3초에 마지막 결과가 오고 3.9초에 정지 신호(끊긴 지 0.63초)가 나가서, 출발점에서 0.633 m 간 곳에 섰다. 마지막 결과 뒤로 12 cm쯤 더 간 것이다. 연결이 돌아오지 않아 그 자리에 서 있다가 시간 초과로 끝났다. 안전하게 서기는 하지만 임무는 못 한다.

## 정리

이 로봇에서는 지연이 문제가 아니었다. 인식 범위 끝에서 사각지대 경계까지가 1.27 m라 초속 0.25 m면 허용 지연이 5초쯤인데, 두 방식 모두 실제 지연이 허용 지연보다 훨씬 작다. 고를 때 기준이 되는 건 연결이 끊겼을 때 기능을 잃는지(PC 추론은 0.6초 안에 서야 한다)와 원본 영상 대역폭이다. 반대로 로봇에서 추론할 때 쓰는 1코어는 Nav2와 CPU를 다툴 때 문제가 됐다. CPU 과부하로 카메라 point가 늦게 도착하자, 이를 Nav2가 오래된 데이터로 보고 7분 동안 계속 버렸다. 인식 노드는 point를 정상적으로 발행하고 있어서 겉으로는 문제가 없어 보였다. 감시 노드는 이 일을 겪은 뒤 만들었다.
